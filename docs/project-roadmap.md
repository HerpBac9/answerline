# Дальнейшее развитие Answerline

## Решение по схеме знаний

В RAG хранится **один полный ответ на один вопрос**. База не разделяется на
`SHORT_ANSWER` и `LONG_ANSWER`, и для одного вопроса не создаются несколько
vector points. Это сохраняет чистый retrieval и не создаёт конкуренцию между
одинаковыми вопросами.

Текущий prompt ограничивает один подготовленный ответ максимум 5000 символами,
но не требует заполнять весь лимит. Runtime может ответить короче в зависимости
от вопроса и system prompt, однако структура источника и индекса остаётся
единой.

## Этап 1. Увеличить и измерить RAG context

**Приоритет: самый высокий.**

Цель — передавать модели больше полезного полного evidence, не меняя формат
Q&A-файлов и не создавая дополнительные answer-поля в индексе.

### План

1. Зафиксировать baseline на текущих настройках:

   ```text
   RAG_GENERAL_TOP_K=3
   RAG_PERSONAL_TOP_K=1
   RAG_MAX_CONTEXT_TOKENS=4000
   ```

2. Последовательно проверить `RAG_MAX_CONTEXT_TOKENS=6000`, `8000` и `10000` на
   одном embedding, одной LLM и одном evaluation-наборе.
3. Перед каждым прогоном проверить context length модели в LM Studio. Общий
   prompt включает system prompt, историю, transcript, RAG evidence и резерв
   `LLM_MAX_TOKENS`; лимит RAG нельзя рассматривать отдельно.
4. Сравнивать для каждого режима:
   - `ragContextTokens` и `promptEstimateTokens`;
   - количество реально вошедших evidence-блоков;
   - retrieval latency и TTFT;
   - полное время ответа и tokens/s генерации;
   - ошибки переполнения context window;
   - полноту, groundedness и фактическую правильность ответа.
5. Проверить, не вытесняет ли длинный первый ответ следующие релевантные chunks
   из-за текущего последовательного token cap.
6. Если 10000 ухудшает latency или вызывает переполнение, оставить меньшее
   значение. Не менять `LLM_MAX_TOKENS` одновременно с RAG-лимитом.
7. Зафиксировать выбранное значение в `.env.example`, `command.md`, статусе и
   benchmark-отчёте.

### Критерии готовности

- выбран context budget с измеримым улучшением полноты evidence;
- нет ошибок переполнения на реальном context window модели;
- TTFT и memory usage остаются приемлемыми для MacBook с 16 ГБ RAM;
- исходные Q&A-файлы и payload остаются в текущем формате;
- Windows и macOS используют одинаковую логику budget.

## Этап 2. Качество retrieval

**Приоритет: высокий.**

- Собрать golden set из реальных вопросов, перефразировок и ожидаемых модулей.
- Разделить retrieval miss, плохой chunk и ошибку генерации.
- Добавить FTS5/BM25 или другой sparse-канал к dense search.
- Сравнить reciprocal-rank fusion, текущий lexical boost и dedicated reranker.
- Добавить фильтры по `authority`, `document_type`, module и статусу факта.
- Проверять provenance и citation correctness.
- Отдельно измерять Recall@k, MRR/nDCG, groundedness, answer correctness,
  latency и prompt tokens.

### Критерии готовности

- есть воспроизводимый evaluation report;
- критичные вопросы находят нужный модуль в top-1/top-5;
- улучшение retrieval не увеличивает неприемлемо TTFT;
- неавторизованные или устаревшие факты не попадают в evidence.

## Этап 3. Индекс и свежесть данных

**Приоритет: средний.**

- Проверять `source_sha256` перед запуском или автоматически предлагать
  переиндексацию.
- Разделить canonical project facts, external learning material и drafts на
  разные коллекции или namespaces.
- Добавить отчёт о новых, изменённых, удалённых и дублирующихся вопросах.
- Сделать атомарную смену коллекции: backfill → evaluation → switch → rollback.
- Зафиксировать parser/chunker/embedding version в payload.
- Сохранить один полный answer на запись и не дублировать вектор ради разных
  режимов ответа.

## Этап 4. Производительность локального стека

**Приоритет: средний.**

- Снять benchmark embedding cold/warm, Qdrant и LLM отдельно.
- Контролировать память LM Studio, Whisper и Qdrant на 16 ГБ Mac.
- Добавить динамический context budget, зависящий от доступного context window.
- Уменьшать шум evidence только после измерения, а не простым усечением
  полного ответа без проверки смысла.
- Сохранять в отчёте выбранный RAG budget, top-K, model context length и
  `LLM_MAX_TOKENS`.

## Этап 5. macOS production hardening

**Приоритет: высокий перед реальным использованием на Mac.**

- Проверить чистую установку на актуальном macOS и Apple Silicon.
- Проверить microphone/System Audio Recording permissions после первого запуска.
- Проверить CoreAudio helper после sleep/wake, смены устройства и закрытия.
- Проверить `.app`, DMG, hardened runtime и entitlements на чистом профиле.
- Провести реальный тест в используемом conferencing client и записать
  ограничения capture protection.
- Явно показывать пользователю, какой канал захвата недоступен и почему.

## Этап 6. Windows regression и packaging

**Приоритет: высокий перед публикацией общей версии.**

- Проверить, что изменения macOS не меняют WASAPI contract и Windows IPC.
- Проверить Windows 10/11, PowerShell, native module ABI и Whisper lifecycle.
- Собрать установочный пакет и проверить обновление поверх старого config.json.
- Проверить глобальные hotkeys, sleep/resume и закрытие процесса.

## Этап 7. Качество подготовки знаний

**Приоритет: средний.**

- Использовать `document:extract` для PDF/DOCX/HTML, затем проверять extraction
  отдельно от LLM-генерации.
- Подготовить правила для формул, таблиц, кодовых блоков и OCR review.
- Генерировать вопросы от базовых к Tech Lead, не заполняя корпус шаблонными
  вопросами ради количества.
- Валидировать каждый ответ по исходному документу и отделять источник от
  инженерного синтеза.
- Ограничивать подготовленный полный ответ 5000 символами без потери ключевых
  фактов, причин, ограничений и практических последствий.
- Переводы сохранять через checkpoint, затем отдельно проверять термины,
  числа, версии и падежи.

## Этап 8. Наблюдаемость и восстановление

**Приоритет: средний.**

- Оставить benchmark-метрики без текста транскрипта и ответа по умолчанию.
- Для обычных сессий сохранять отдельный локальный JSONL trace: вопрос, embedding,
  retrieval candidates/context, prompt estimates, TTFT и ответ; это позволяет
  разделять retrieval miss и ошибку генерации.
- Логировать стадии: capture, STT, embedding, retrieval, prompt, TTFT, output.
- Добавить correlation/session ID в probes и RAG evaluation.
- Сделать явное восстановление после падения document/translation pipeline.
- Проверить, что partial answer не попадает в историю после отмены.

## Что не является ближайшей целью

- Облачный STT/LLM без отдельного решения по приватности.
- Гарантированная невидимость overlay во всех screen-sharing клиентах.
- Разделение RAG-базы на short/long answer или дублирование одного вопроса в
  нескольких vector points ради разных режимов ответа.
- Автоматическое доверие к ответу модели без проверки evidence и backend-инвариантов.
