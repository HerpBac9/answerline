# Индексация interview Q&A в RAG

Исходные документы находятся в `data/`. Индексатор читает верхнеуровневые
Markdown-файлы корпуса и исключает `data/AGENTS.md` (если файл присутствует),
чтобы инструкции для агента не стали поисковыми evidence. Каждый заголовок `##`
считается самостоятельной записью: заголовок — `question`, следующий текст до
следующего `##` — `answer`. Служебная разметка ответа вырезается на разборе:
строки-классификаторы `**Уровень:** ...` и ведущий маркер `**Ответ:**` не
попадают в payload. YAML front matter используется для языка, роли и подписи
модуля, но стабильная taxonomy берётся из имени файла.

## Идентификатор и payload

Логический ключ записи:

```text
<module_slug>::<normalized_question>
```

Например: `ai-agent-orchestration::чем ai-агент отличается от чат-бота с rag?`.
Qdrant принимает в качестве point ID только UUID или uint64, поэтому технический
ID — детерминированный UUID из SHA-256 логического ключа. Когда существует
`data/manifest.jsonl`, `payload.record_key` переносит стабильный ID записи из
манифеста (например `my-topic.my-section-dcbcab02`); без манифеста
индексатор использует fallback `module::raw question`. Человекочитаемый исходный
вопрос всегда остаётся в `payload.question`.

В payload также сохраняются `module`, `module_label`, `question`, `answer`,
`source_file`, `source_sha256`, `section_index`, `language`, `target_role` и
`embedding_model`. Это позволяет показать источник ответа и отфильтровать поиск
по модулю без повторного чтения Markdown.

Для embedding индексируется только retrieval-ключ, а полный ответ остаётся в
payload и попадает в prompt только после выбора кандидата:

```text
module: <module_slug>
question: <question>
tags: <manifest tags, если есть>
```

Алиасы в embedding не входят: они сохраняются в payload, участвуют в lexical
rerank, а для вариантных корпусов каждый вариант и так получает собственный
вектор. Ответ намеренно не включается в embedding: пользовательский запрос
является вопросом, а длинный ответ содержит повторяющиеся шаблоны и размывает
question-to-question similarity.

Для обычных Markdown-источников aliases (алиасы — альтернативные формулировки
того же вопроса) остаются в payload исходного вопроса и участвуют в lexical
rerank, но не создают отдельные точки. Вариантные корпоры используют другой
контракт: пара файлов `<prefix>_interview_knowledge_base_ru.md` +
`<prefix>_question_variants.json` (например,
`rag_500_interview_knowledge_base_ru.md` + `rag_500_question_variants.json`).
Sidecar JSON связывает один канонический вопрос с его вариантами, а индексатор
создаёт отдельный Qdrant point для канонического вопроса и каждого варианта.
Обычно один-два варианта на запись; запись без вариантов также допустима —
канонический вопрос всё равно получает свой вектор (так устроен хвост
`llm_serving`-корпуса).
У всех points одной группы одинаковые `record_key`, `question`, `answer` и
`section_index`; поле `matched_question` показывает, какой текст конкретного
вектора нашёл пользовательский запрос, а `variant_index` — его порядковый
номер. Runtime дедуплицирует такие hits по `record_key`, поэтому в prompt
попадает один ответ, а не несколько копий.

Личный контур объединяется по полю `authority`: любой файл, объявивший
`authority: internal_project` или `personal_experience`, попадает в личный поиск,
независимо от имени. Это позволяет не смешивать происхождение данных и
одновременно искать проектный опыт в одной
секции `<personal_experience>`.

Каждая запись также получает `authority`: `general_knowledge` для общего
теоретического корпуса, `external_source` для проверенных внешних материалов,
`internal_project` для подтверждённых проектных фактов и
`personal_experience` для ответов о личном опыте. Смешанные файлы классифицируются
на уровне H2-секции. General-поиск исключает последние два authority, а personal-
поиск включает их вместе с модулями проекта.

Authority приходит из YAML front matter самого файла в `data/`.
`scripts/prepare-rag-corpus.mjs` переносит его в `data/manifest.jsonl`; если у
записи нет манифеста, индексатор берёт `authority` из front matter самой
записи, а без обоих источников поле остаётся пустым. Файл без `authority`
получает `general_knowledge`, поэтому личный опыт попадает в личный контур
только явным `authority: internal_project` в его front matter. Карты модулей в
репозитории нет: чтобы добавить личный корпус, достаточно дописать ключ в его
файл, код менять не нужно.

Суффикс `_interview_knowledge_base_ru` в имени файла включает вариантный
режим: одна каноническая запись на группу вариантов из одноимённого
`*_question_variants.json`. Файл без этого суффикса разбирается как
самостоятельные вопросы, где каждая `##`-секция — сам по себе вопрос.

## Известное ограничение: concept_group

`slug()` в `prepare-rag-corpus.mjs` оставляет только `[a-z0-9]`, поэтому у
вопроса, целиком написанного по-русски, `concept_group` схлопывается в
буквальное `"question"`: групп столько же, сколько записей с латиницей в
заголовке. Группировать по `concept_group` русский корпус нельзя. На
уникальность id это не влияет, на поиск при retrieval — тоже, поэтому чинить
пришлось бы переписыванием заголовков корпуса, и в текущем цикле работ этого
не делалось.

## Пересборка манифеста

`prepare-rag-corpus.mjs` по умолчанию **не пересобирает** сгенерированные поля:
`tags`, `expected_facts`, `concept_group`, `type` берутся из предыдущего
`data/manifest.jsonl`, если он есть. Это сделано, чтобы `expected_facts` и теги
не плясали заново при каждом запуске, но у этого есть цена: если `.md` правили
руками, манифест продолжает хранить старое. Именно так в репозитории оказался
манифест, разошедшийся с корпусом — у `an external company-ai-solution-architect` в нём
было на 90 секций меньше, чем `##` в файле.

Полная пересборка — `RAG_REBUILD_METADATA=1 npm run rag:prepare`. Без него
запускать препаратор после ручной правки корпуса бессмысленно.

Скрипт не принимает `--data` / `--out`: путь к корпусу задаётся переменной
окружения `RAG_DATA_DIR`. Это важно, потому что запуск без неё переписывает
`data/*.md` и `data/manifest.jsonl` в самом репозитории — сухой прогон надо
делать на копии. Побочный эффект: `writeFileSync` в препараторе пишет CRLF в
части файлов, где раньше был LF, и diff становится нечитаемым по всему файлу
вместо изменений во фронтматтере.

## Правило вложенности

`data/*.md` читают два индексатора, и оба молчат про нарушение структуры, а не
падают: `##` — это один вопрос и один чанк, а `###` не попадает ни в чанк, ни
в банк вопросов для тренировки, а просто едет текстом ответа чанка над ним.
Вложенная раскладка `## 1. Модуль` / `### 1.1. Вопрос` поэтому не «работает
хуже» — она перестаёт индексироваться: банк вопросов принимал одну секцию, и
это была секция «Как устроен этот документ».

`src/main/training/corpusLayout.test.ts` фиксирует этот инвариант для
генерируемых корпусов: все секции на `##`, ни одного `###` и ни одного
заголовка, который не читается как вопрос.

## Модель

Текущий live-индекс использует `Qwen3-Embedding-0.6B` через LM Studio с моделью
`text-embedding-qwen3-0.6b-text-embedding` (1024 измерения). Скрипты проверяют
размерность перед upsert и во время `doctor`. Важно использовать один и тот же
model id и одинаковый формат query/document для индексации и runtime. Коллекция
с 4096 измерениями относится к старому 8B baseline, а
коллекция на 768 измерений — к старому EmbeddingGemma-300M индексу; ни одну из
них нельзя смешивать с текущим 1024-мерным индексом.

Для Qwen3-Embedding индексатор отправляет запросы с instruct-префиксом
`Instruct: Given a technical interview question, retrieve relevant passages
that answer the question`, а документы — без префикса. После смены модели или
формата пересоберите коллекцию с `RAG_RECREATE=1 npm run rag:index`.

Runtime запрашивает расширенный semantic top-K, затем выполняет дешёвый hybrid
rerank: cosine score сохраняется как основной сигнал, а пересечение содержательных
слов вопроса с заголовком кандидата добавляет небольшой lexical boost. Это защищает
точные идентификаторы и аббревиатуры вроде `SLI`, `SLO`, `checkpoint` и `RAG`, не
отказываясь от semantic retrieval для перефразировок.

Для каждого вопроса выполняется один embedding, после чего Qdrant получает два
запроса параллельно. Первый фильтрует по authority `internal_project` / `personal_experience`
и оставляет лучший top-1 в `<personal_experience>`.
Второй исключает эти authority через `must_not` и оставляет до трёх
общих теоретических ответов в `<knowledge_context>`. Оба контура
фильтруются по исходному semantic score: personal-кандидат отбрасывается ниже
`RAG_PERSONAL_MIN_SCORE`, general-кандидаты — ниже `RAG_MIN_SCORE`, поэтому при
слабом совпадении секция может остаться пустой. Reranked score (semantic +
lexical boost) для порогов не используется.

`BAAI/bge-m3` — следующий кандидат для A/B-проверки: 1024 измерения, контекст до
8192 токенов, более 100 языков, dense+sparse возможности. Его модельная карта
рекомендует hybrid retrieval (BM25/FTS + dense) с reranking, поэтому он особенно
интересен после подключения lexical-ветки. Нельзя смешивать в одной коллекции
векторы разных моделей или размерностей; для A/B нужны разные коллекции.

Для решения оставляем набор воспроизводимых тестовых вопросов и сравниваем
`Recall@k`, `MRR@k`, правильность `module` и долю ответов, где найденный chunk
действительно подтверждает формулировку. Средний similarity сам по себе не
является доказательством релевантности.

## Запуск

1. Запустить локальный Qdrant на `http://127.0.0.1:6333`.
   Например, при установленном Docker:

   ```powershell
   docker run --name answerline-qdrant -p 6333:6333 -v qdrant_storage:/qdrant/storage qdrant/qdrant
   ```

   В текущем окружении порт `6333` пока не поднят, поэтому фактический upsert
   выполняется после запуска Qdrant.
2. Загрузить в LM Studio embedding-модель и включить OpenAI-compatible server
   на `http://127.0.0.1:1234`.
3. Скопировать `.env.example` в `.env` и проверить `EMBEDDING_MODEL` по точному
   ID модели, который отдаёт сервер.
4. Проверить разбор документов без обращения к серверам:

   ```powershell
   npm.cmd run rag:index -- --dry-run
   ```

5. Построить/обновить коллекцию:

   ```powershell
   npm.cmd run rag:index
   ```

6. После удаления или переименования вопросов выполнить чистую пересборку:

   ```powershell
   $env:RAG_RECREATE = '1'; npm.cmd run rag:index
   ```

Обычный запуск делает deterministic upsert. Для удаления устаревших chunks нужен
явный recreate, чтобы случайно не потерять работающий индекс.

Если нужно пересобрать только manifest, не переписывая исходные Markdown:

```bash
RAG_MANIFEST_ONLY=1 npm run rag:prepare
```

## Runtime-контракт

`Session` использует `LocalRag` для каждого вопроса: он один раз вызывает
embeddings, параллельно делает personal-only и general-only semantic поиск,
выполняет hybrid rerank обоих контуров, оставляет top-1 личного кандидата и
top-3 общих кандидата после score-фильтрации, затем ограничивает итоговый
`<retrieved_context>` только параметром `RAG_MAX_CONTEXT_TOKENS`. Score
сохраняется в evidence и метриках для диагностики.
Контекст добавляется только в текущий user-turn; в историю сохраняется вопрос без
retrieved chunks. Системный prompt остаётся неизменным, а найденные записи
помечены как untrusted evidence и не могут менять инструкции. Для короткого
уточнения, начинающегося с «а», «и», «тогда» или «теперь», Session добавляет к
retrieval query предыдущий вопрос. Это помогает найти правильную тему для фраз
вроде «А какие фреймворки вы использовали?», но в сам вопрос, который получает
модель, предыдущий вопрос автоматически не подменяется.

`knowledge/` больше не читается приложением. Источником правды для retrieval
являются `data/*.md` и их `source_sha256`; `data/AGENTS.md` намеренно исключён.
После изменения данных выполняйте индексацию и `npm.cmd run rag:evaluate`.
